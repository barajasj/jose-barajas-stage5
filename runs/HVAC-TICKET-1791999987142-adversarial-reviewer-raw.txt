**Challenges Report – Ticket 01**

| Category | Findings |
|----------|----------|
| **Unsupported Assumptions** | 1. The interpreter assumes that *all* circuit heights are always present and numeric; real‑world data may include null, “‑”, “N/A”, or placeholder values.<br>2. It presumes a one‑to‑one mapping between “Cooling Circuits” and UI fields; the system could store circuits in a separate table or as a JSON array, which changes how the sum is computed.<br>3. Assumes the DX‑Coil Height field is **only** displayed after calculation, ignoring possible requirements to show a placeholder (e.g., “—”) or a pre‑populated default. |
| **Missing Requirements** | 1. **Persistence** – No guidance on whether the calculated height must be saved to the database, synced to backend services, or remain purely client‑side.<br>2. **Audit Trail** – No requirement to log when a user edits a circuit height and triggers a recalculation (useful for compliance/re‑work traceability).<br>3. **Bulk Edit Handling** – If a user modifies multiple circuit heights before leaving the form, the interpreter does not specify whether the system should recalc after each keystroke or after the edit session ends (e.g., on blur or “Save”).<br>4. **Performance Constraints** – No mention of handling large numbers of circuits (e.g., > 100) or ensuring the UI remains responsive. |
| **Incorrect HVAC Interpretations** | 1. The term **“Cooling Package (e.g. R‑454B FW 43 )”** is treated as a generic label, but in HVAC engineering this denotes a *specific* refrigerant‑based package with defined coil geometry, pressure drops, and design limits. Those limits may impose a maximum allowable DX‑Coil Height that the interpreter never addresses.<br>2. The interpreter does not differentiate between **“DX Coil”** (direct‑expansion) and a **“Water‑Cooled Coil”** that might coexist in the same package; summing heights may be inappropriate for mixed‑type packages. |
| **Missing Validation Rules** | 1. **Range Checks** – Circuit heights should be bounded (e.g., 0 in < height ≤ 30 in) to prevent unrealistic totals.<br>2. **Unit Consistency** – Validation must enforce that all heights use the same unit (inches, mm) before summation.<br>3. **Duplicate/Null Detection** – The system should flag duplicate circuit identifiers or missing height entries prior to calculation.<br>4. **Numeric Precision** – Define allowed decimal precision (e.g., two decimal places) and behavior for rounding errors that could accumulate across many circuits. |
| **Missed Ambiguities** | 1. **When does the initial calculation occur?** – The description says “when we enter the Cooling Package the system will run to Calculations,” but it is unclear whether this is on package selection, on page load, or after the user confirms the package.<br>2. **User Edit Trigger** – Is the DX‑Coil Height updated **live** (on each keystroke) or **after** the user leaves the field? The wording “react to this edit – resum[e] all heights and update” is ambiguous.<br>3. **Circuit Count Variability** – No explicit limit on the number of circuits; can circuits be added/removed dynamically after the initial load?<br>4. **Display Format** – Should the result be shown with units (e.g., “22.5 in”) or raw numeric value? Should trailing zeros be trimmed?<br>5. **Error Presentation** – If a circuit height is invalid, how should the UI notify the user? Inline error, tooltip, modal?<br>6. **Concurrency** – If multiple users edit the same package simultaneously, how is the DX‑Coil Height kept consistent across sessions? |

### Summary
The interpreter’s output captures the high‑level intent (sum circuit heights → DX‑Coil Height) but omits critical engineering constraints, persistence semantics, validation detail, and precise UI behaviour. Addressing the unsupported assumptions, missing requirements, inaccurate HVAC context, absent validation rules, and unresolved ambiguities is essential before a reliable implementation can be specified.
